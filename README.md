# LedgerSchool — Fees Management System

A responsive admin dashboard for managing classes, students and fee payments,
built with plain HTML/CSS/JavaScript and Supabase (Postgres + Auth). No build
step, no frameworks — just open `index.html` after a few minutes of Supabase
setup.

## 1. Create a Supabase project

1. Go to [supabase.com](https://supabase.com) → **New project**.
2. Once it's ready, open **SQL Editor → New query**, paste the entire
   contents of `sql/schema.sql`, and run it. This creates the three tables
   (`classes`, `students`, `fee_records`), the auto-calculation triggers, the
   fee-generation functions, and Row Level Security policies.
3. Open **Authentication → Users → Add user** and create your first admin
   login (email + password). Public sign-up is intentionally not wired into
   this app — only `signInWithPassword` is used, so only accounts you create
   manually can log in.

## 2. Connect the app to your project

Open `js/config.js` and replace the two placeholder values:

```js
const SUPABASE_URL = "https://YOUR-PROJECT-REF.supabase.co";
const SUPABASE_ANON_KEY = "YOUR-ANON-PUBLIC-KEY";
```

Both are on **Project Settings → API** in the Supabase dashboard. The anon
key is safe to ship in client code — every table is protected by Row Level
Security so only authenticated admins can read or write.

## 3. Run it

There's no build step. Either:

- Open `index.html` directly in a browser, or
- Serve the folder with any static server (recommended, avoids some browser
  `file://` quirks), e.g.:
  ```bash
  npx serve .
  # or
  python3 -m http.server 8080
  ```

Log in with the admin account you created in step 1.

## How fee generation works — manual only

Fee records are **never** created automatically anywhere in the app —
not when a student is added, not when a class is edited. The single way any
fee record comes into existence is the **Generate Fees for a Period** button
on the Fee Records page. This is intentional: the admin decides exactly when
a billing period opens.

The dialog has:

- **A Monthly / Yearly toggle** for which kind of period to generate.
- **A student lookup**, defaulted to "All active students." Leave it as-is
  to generate for every eligible active student at once, or pick one
  student to generate just theirs (handy right after adding someone new, or
  to backfill a single student who was missed).
- **Academic Year** (+ **Month**, for Monthly) fields.

Rules enforced at the database level, regardless of how the dialog is used:

- Only **active** students in an **active** class of the matching fee type
  are eligible.
- A student is **never given a Monthly record for a year in which they
  already have a Yearly record** — Monthly generation silently skips them.
  A student is meant to be on one plan or the other, not both.
- **Duplicates are impossible.** Partial unique indexes (`uq_fee_monthly`,
  `uq_fee_yearly`) back every insert, so re-running generation for a period
  that's already been generated — for one student or for everyone — never
  creates a second record. It's safe to click the button again if you're
  ever unsure whether it already ran.
- **Deactivated students** are excluded automatically.

## Deleting fee records

Every row in the Fee Records table has a **Delete** button. It asks for
confirmation (this also permanently removes any payment recorded against
that record) and cannot be undone. Use this to remove a record generated by
mistake — for example, wrong month, wrong student, or a duplicate created
before this app's duplicate protection was in place.

## Payments: amount paid + discount

Recording a payment now captures two independent numbers:

- **Amount Paid** — money actually received.
- **Discount Amount** — a waiver/concession that reduces what's owed
  without counting as money received.

Both count toward closing out the balance:
`balance = fee_amount − amount_paid − discount_amount`. The payment status
(`Pending` / `Partially Paid` / `Paid`) is derived from that same balance.
The dialog shows a live "New Balance" preview as you type, and the database
trigger recalculates and clamps both fields server-side on every write, so
the numbers can never drift out of sync no matter what touches the table.

## Automatic balance & status calculation

A `BEFORE INSERT OR UPDATE` trigger on `fee_records` recalculates
`balance_amount` and `payment_status` every time a row is written — the app
never computes these client-side, so they stay correct no matter which
client or SQL script touches the table.

## Suggested monthly routine

At the start of each month: open **Fee Records → Generate Fees for a
Period**, leave the student lookup on "All active students," keep it on
"Monthly," confirm the year/month, and click **Generate Records**. Running
it again later (or by accident) is harmless — existing records are never
touched or duplicated.

## Upgrading an existing installation

If you already ran an earlier version of `sql/schema.sql`, just run the
**entire file again** — it's written to be safely re-run. It will:

- add the new `discount_amount` column if it isn't there yet,
- replace the calculation trigger with the discount-aware version,
- drop the old 2-parameter `generate_monthly_fees` / `generate_yearly_fees`
  functions and the old auto-generation-on-create function, and recreate
  the generation functions with the new optional student parameter.

No existing data is touched or lost.
